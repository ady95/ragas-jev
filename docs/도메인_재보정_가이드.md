# 도메인 재보정 가이드

RAGAS-JEV를 새 서비스 도메인에 적용할 때, JEV 확률 보정(calibration)을 그 도메인의 사람 라벨로 다시 학습하는 절차다.

## 왜 필요한가

- 기본 보정 파일(`src/ragas_jev/data/calibration_jev-1.13.0.json`)은 MIRACL, RAGTruth, 합성 한국어·영어 데이터로 학습했다.
- isotonic 보정은 "이 JEV 확률에서 실제로 yes인 비율"을 배우므로, 학습 데이터의 **라벨 비율**까지 담는다. 예를 들어 같은 문구의 질문이 Faithfulness 데이터에서는 확률을 올리는 쪽으로, Context Recall 데이터에서는 내리는 쪽으로 보정됐다 ([Phase 5 리포트](reports/phase5_routing_calibration.md) 5.3절).
- 서비스 데이터의 hallucination 비율이나 관련 passage 비율이 벤치마크와 다르면 기본 보정은 맞지 않는다. 보정이 틀리면 점수와 routing(LLM 재검증 대상 선택)이 함께 틀어진다.

## 언제 하는가

- 새 도메인에 처음 적용할 때
- JEV 모델 버전을 바꿨을 때 (`TYPESAFE_DEFAULT_MODEL`)
- 판정 문항 버전을 바꿨을 때 (예: `claim_support.v1` → v2)
- 사람 검토 결과와 자동 점수가 자주 어긋날 때

## 데이터 보호

- 라벨 시트에는 판정에 필요한 질문, 평가 단위, 근거 텍스트가 들어간다. 마스킹은 기본으로 꺼져 있다. `calibration sample --pii-masking` 또는 `RAGAS_JEV_PII_MASKING=true`로 켜면 평가 때와 같은 방식으로 **마스킹된 텍스트**만 들어간다. 평가를 마스킹 없이 했더라도 시트의 평가 단위 텍스트까지 마스킹한다.
- 라벨 시트는 로컬에서만 다룬다. `results/`나 `.cache/` 아래에 두면 git에서 제외된다.
- 라벨링과 재보정 자체는 외부 API를 호출하지 않는다. 단, 라벨 시트를 만들기 전 `evaluate` 단계는 LLM 프록시와 JEV(모두 국외)를 호출하므로, 실제 고객 데이터를 쓰려면 먼저 보안·법무 검토를 통과해야 한다.

## 절차

### 1. 평가 실행

서비스 데이터 표본을 평소처럼 평가한다. 재보정용이므로 보정과 routing은 꺼도 된다 (JEV 원래 확률 `jev_p`는 어느 경우든 결과에 남는다).

```bash
uv run ragas-jev evaluate -i results/domain_samples.jsonl -o results/domain_results.jsonl --no-audit
```

### 2. 라벨 시트 만들기

```bash
uv run ragas-jev calibration sample -r results/domain_results.jsonl -s results/domain_samples.jsonl \
  -o results/label_sheet.csv --per-key 300
```

- 문항 × 언어별로 최대 300개 unit을 뽑는다. JEV 확률 구간(0.0~0.1, …, 0.9~1.0)마다 고르게 뽑아 확률 범위 전체를 덮는다.
- 확률 구간별로 뽑아도 보정이 편향되지 않는다. 보정은 "확률이 p일 때 yes일 비율"을 추정하는 것이라 전체 yes 비율과 무관하다.
- 사람 검토 대기열(`review export`)의 라벨만으로 재보정하지 않는다. 그 unit들은 JEV와 LLM이 엇갈린 어려운 사례에 몰려 있다.

### 3. 라벨 채우기

`label` 열에 **1(yes)** 또는 **0(no)**을 적는다. 빈 칸은 학습에서 빠진다. 시트는 UTF-8(BOM 포함)이라 Excel에서 한글이 깨지지 않는다.

| 열 | 내용 |
|---|---|
| `question_id` | 판정 문항 (아래 기준 참고) |
| `question` | 원래 질문 |
| `unit_text` | 판정 대상 (claim, statement 또는 passage 번호) |
| `evidence` | 판단 근거: Context Precision은 해당 passage, Faithfulness·Recall은 전체 contexts, Answer Relevancy는 전체 답변 |
| `jev_p` | JEV 원래 확률 (라벨링할 때는 보지 않는 것이 좋다. 열을 숨기고 작업한다) |

문항별 기준:

| 문항 | label = 1 | label = 0 |
|---|---|---|
| `chunk_relevance.*` (Context Precision) | passage(`evidence`)가 질문에 답하는 정보를 담고 있다 | 주제나 개체만 같고 답은 없다 |
| `claim_support.*` (Faithfulness) | claim의 모든 부분(숫자·날짜·이름 포함)이 contexts에 있거나 contexts에서 바로 도출된다. **자기 지식은 근거가 아니다** | 일부가 contexts에 없거나 다르거나 반대된다 |
| `ref_claim_coverage.*` (Context Recall) | 위와 같음 (reference claim 기준) | 위와 같음 |
| `statement_relevance.*` (Answer Relevancy) | 질문에 답하거나 답에 도움이 되는 질문 대상 정보다 (참·거짓은 따지지 않는다) | 다른 대상의 이야기이거나 군더더기다 |

라벨 수 기준:

- 문항 × 언어당 **최소 100개**가 있어야 새 보정을 학습한다 (`--min-labels`). 그보다 적으면 기본 보정을 그대로 쓴다.
- 안정적인 결과를 위해 **300개 이상**을 권장한다. 특히 yes/no 한쪽이 10% 미만으로 드문 경우 더 많이 필요하다.

### 4. 재보정

```bash
uv run ragas-jev calibration fit -l results/label_sheet.csv -o results/domain_calibration.json
```

여러 시트를 함께 쓸 수 있다: `-l sheet1.csv -l sheet2.csv`. 출력 예:

```text
  key | labels | yes rate | ECE raw | ECE base map | ECE new map (cross-validated) | result
  claim_support.v1:ko | 300 | 0.82 | 0.071 | 0.064 | 0.018 | fitted
  chunk_relevance.v2:ko | 42 | 0.21 | 0.188 | 0.030 | - | fewer than 100 labels: kept the base map
```

읽는 법:

- `ECE raw`: JEV 원래 확률의 보정 오차
- `ECE base map`: 기본 보정 파일을 이 도메인 라벨에 적용했을 때의 오차. **이 값이 충분히 작으면(예: 0.03 이하) 재보정 없이 기본 보정을 써도 된다** (`evaluate --calibrate`)
- `ECE new map (cross-validated)`: 새 보정의 오차. 같은 샘플을 학습과 평가에 함께 쓰지 않는 5-fold 교차 검증 값이다
- 새 보정의 오차가 기본 보정보다 크지 않으면, 라벨이 부족하거나 도메인 차이가 작은 것이다

### 5. 적용

```bash
uv run ragas-jev evaluate -i data.jsonl -o results/out.jsonl --calibration results/domain_calibration.json
# 또는 .env에 RAGAS_JEV_CALIBRATION_FILE=results/domain_calibration.json
```

결과의 `evaluation_model.calibration`에 사용한 보정 파일 설명이 기록된다.

## routing 정책도 다시 봐야 하는가

metric별 routing 정책(`DEFAULT_METRIC_POLICIES`)은 벤치마크 데이터의 시뮬레이션으로 정했다 ([Phase 5 리포트](reports/phase5_routing_calibration.md)). 보정을 바꾸면 confidence 분포도 바뀌므로, 사람 라벨이 충분하면 같은 방식으로 정책도 다시 정하는 것이 좋다. 그러려면 라벨링한 unit에 대한 Auditor·Strong Judge 판정이 필요하다 (`benchmark/run_phase5.py`의 방식 참고). 라벨이 적으면 기본 정책을 유지한다.
