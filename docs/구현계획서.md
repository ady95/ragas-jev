## 1. 개요

### 1.1 목표

설계방향 문서의 3계층 구조를 실행 가능한 Python 평가 파이프라인으로 구현한다.

```text
LLM은 문제를 나누고 (Preprocessor)
JEV는 판단하고      (Primary Judge)
프로그램은 점수를 계산한다 (Deterministic Scorer)
```

### 1.2 구현 범위

| 구분 | 포함 | 제외 (후속) |
|---|---|---|
| Metric | Faithfulness, Context Precision(soft/rank), Context Recall, Answer Relevancy | Noise sensitivity, Answer correctness 등 기타 RAGAS metric |
| Judge | JEV Primary Judge (Noul / Score / Choice), LLM Auditor, Strong Judge | JEV 모델 자체 학습·튜닝 |
| 산출물 | 샘플 단위 결과 JSON, 데이터셋 집계 리포트, 벤치마크 리포트 | 웹 대시보드 |
| 실행 형태 | Python 라이브러리 + CLI | 상시 서비스(API 서버) |

### 1.3 완료 기준

1. 4개 metric 모두 설계방향 문서 15장의 결과 schema로 산출된다.
2. 모든 판단 단위(claim/chunk/statement)에 `p`, `confidence`, `uncertainty`, `decision_source`가 기록된다.
3. confidence 구간에 따라 JEV 결과 사용 / LLM Auditor / Strong Judge·Human Review로 분기된다.
4. 동일 입력·동일 캐시 상태에서 점수가 비트 단위로 재현된다 (Scorer는 순수 함수).
5. 기존 RAGAS, JEV-only, Hybrid 3종 비교 벤치마크 리포트가 생성된다.

## 2. 실행 환경 및 설정

### 2.1 `.env` 변수 해석

| 변수 | 용도 | 사용 모듈 |
|---|---|---|
| `OPENAI_BASE_URL` | 사내 openai-oauth 로컬 프록시 엔드포인트 (OpenAI SDK가 자동 인식) | Preprocessor, Auditor |
| `OPENAI_API_KEY` | 프록시 사용 시 더미값 (`not-needed`) | Preprocessor, Auditor |
| `OPENAI_MODEL` | 기본 생성 모델 (`gpt-6-luna`, 2026-09-23 변경) | Preprocessor 기본값 |
| `AVAILABLE_MODELS` | 프록시에서 사용 가능한 모델 목록 (선택. 현재 `.env`에는 없음, healthcheck는 프록시 실제 목록으로 검증) | 모델 선택 검증, 벤치마크 |
| `OPENAI_MODEL_IMAGE` | 이미지 생성 모델 | **본 프로젝트 미사용** |
| `TYPESAFE_API_KEY` | JEV(TypeSafe System One API) 인증 키. `typesafe-sdk`가 환경변수에서 자동으로 읽는다 (호출 확인 완료) | JEV Client |

> 프록시 `/v1/models`의 실제 응답에는 `AVAILABLE_MODELS`에 없는 `gpt-6-sol`, `gpt-6-luna`도 포함되어 있다. `AVAILABLE_MODELS`를 갱신하거나 healthcheck에서 실제 목록으로 검증한다.

### 2.2 모델 역할 배정 (초기값, 설정으로 변경 가능)

| 역할 | 기본 모델 | 비고 |
|---|---|---|
| Preprocessor (claim/statement 추출) | `OPENAI_MODEL` (= gpt-6-luna) | 호출량이 가장 많으므로 경량 모델 |
| LLM Auditor (0.60 ≤ conf < 0.85) | `gpt-6-luna` (`RAGAS_JEV_AUDITOR_MODEL`) | JEV 불확실 구간 정확도가 가장 높고 빠름 ([Phase 1 리포트](reports/phase1_context_precision.md) 4.3절) |
| Strong Judge (conf < 0.60) | `gpt-6-sol` (`RAGAS_JEV_STRONG_JUDGE_MODEL`, 2026-09-24 gpt-6-astra에서 변경) | gpt-6-astra는 합성 데이터 생성에 쓰여 자기 판정 편향이 있고 성능 근거가 없었음. 기준선과 같은 모델 |
| 벤치마크 기준선 LLM Judge | `gpt-6-sol` (`RAGAS_JEV_BASELINE_JUDGE_MODEL`) | 가장 강한 비교 대상으로 두어 결론이 부풀려지지 않게 함. Phase 6 RAGAS baseline도 이 모델 사용 |

> 모델 등급 순서는 프록시 제공 측 기준으로 Phase 0에서 확인한다.

### 2.3 신규 설정 항목 (`.env.example`에 추가)

```dotenv
# JEV (typesafe-sdk가 읽는 표준 변수)
TYPESAFE_API_KEY=             # 실제 값은 .env에만 둔다
TYPESAFE_BASE_URL=https://api.typesafe.ai
TYPESAFE_DEFAULT_MODEL=jev-1.13.0   # alias(jev-latest) 대신 버전 고정 → calibration 재현성
JEV_TIMEOUT_SEC=30
JEV_MAX_CONCURRENCY=8         # rate limit 1,200 RPM 이내로 유지

# Routing thresholds (validation 후 calibration)
RAGAS_JEV_CONF_ACCEPT=0.85
RAGAS_JEV_CONF_AUDIT=0.60
RAGAS_JEV_DECISION_THRESHOLD=0.5

# Models
RAGAS_JEV_PREPROCESSOR_MODEL=${OPENAI_MODEL}
RAGAS_JEV_AUDITOR_MODEL=gpt-6-luna
RAGAS_JEV_STRONG_JUDGE_MODEL=gpt-6-sol
RAGAS_JEV_BASELINE_JUDGE_MODEL=gpt-6-sol

# Data protection
RAGAS_JEV_PII_MASKING=true
RAGAS_JEV_CACHE_DIR=.cache/ragas_jev
```

### 2.4 비밀값 관리 (Phase 0 즉시 조치)

- `.gitignore` 추가 완료: `.env`, `.env.*`(`.env.example` 제외), `.cache/`, 결과·review 파일이 무시된다.
- 키 값이 없는 `.env.example`만 저장소에 커밋한다.
- 로그·결과 JSON·예외 메시지에 키 값이 출력되지 않도록 설정 객체의 `__repr__`에서 마스킹한다 (pydantic `SecretStr` 사용).
- `typesafe_sdk` 로거는 `debug` 레벨에서 요청·응답 **본문을 마스킹하지 않는다**. `TYPESAFE_LOG_LEVEL`은 `info` 이하로만 사용한다.

## 3. 데이터 보호 요구사항

조직 정책(고객 민감정보의 국외 서버 이전 금지, 응답 내 고객 PII 미포함)을 파이프라인 설계에 반영한다.

### 3.1 데이터 흐름별 점검

| 호출 경로 | 전송 데이터 | 확인 결과 |
|---|---|---|
| Preprocessor → `OPENAI_BASE_URL` 프록시 | Answer, Reference | 프록시 모델 목록이 `owned_by: codex-oauth`로 표시됨 → upstream은 OpenAI(**국외**)로 판단 |
| JEV Client → `api.typesafe.ai` | Question, Context, Claim | 미국 TypeSafe 서비스, Cloudflare 경유 (**국외**). 고객 요청은 학습에 쓰지 않으며, ZDR(zero data retention)은 enterprise 계약에서만 제공 |
| Auditor → 프록시 | Question, Context, Claim | Preprocessor와 동일 (**국외**) |

**결론: 외부 호출 경로 3개가 모두 국외다.** 조직 정책상 고객 민감정보는 어느 경로로도 보낼 수 없다. PII Guard는 선택 기능이 아니라 필수 게이트로 둔다.

### 3.2 구현 조치

1. **PII Guard 모듈** (`privacy/pii_guard.py`)
   - 외부 호출 직전 단일 진입점에서 모든 텍스트를 통과시킨다.
   - 주민등록번호, 전화번호, 이메일, 계좌/카드번호, 사업자등록번호 등을 정규식 + 사전 기반으로 탐지해 `[PII_PHONE_1]` 형태의 placeholder로 치환한다.
   - 동일 값은 샘플 내에서 동일 placeholder로 치환해 claim 간 일관성을 유지한다 (entailment 판단 보존).
   - 역치환 매핑은 메모리에만 두고 디스크·로그에 저장하지 않는다.
2. **전송 차단 모드**: `RAGAS_JEV_PII_MASKING=true`인데 마스킹 실패(예외)가 나면 해당 샘플을 외부로 보내지 않고 `status=blocked_pii`로 기록한다.
3. **결과물**: 결과 JSON과 리포트에는 마스킹된 텍스트만 저장한다. 원문 저장은 옵션(`--store-raw`)이며 기본 비활성.
4. **PoC 데이터**: 공개/합성 데이터셋으로만 진행한다. 실제 고객 데이터 사용은 보안·법무 검토(TypeSafe DPA, ZDR 계약 여부, OpenAI 경로 대체 가능성)를 통과한 뒤에만 허용한다.

## 6. 데이터 모델

### 6.1 입력 샘플

```python
class RagSample(BaseModel):
    sample_id: str
    question: str
    answer: str
    contexts: list[str]              # retriever 반환 순서 = rank
    reference: str | None = None     # Context Recall에 필요
    metadata: dict = {}
```

입력 포맷: JSONL (1줄 1샘플). CSV는 `contexts`를 JSON 문자열 컬럼으로 받는다.

### 6.2 중간 산출물

```python
class EvalUnit(BaseModel):
    unit_id: str                     # f"{sample_id}:{kind}:{idx}"
    kind: Literal["claim", "statement", "ref_claim", "chunk"]
    text: str
    source_span: str | None          # 원문 대응 구간 (추적용)

class Decision(BaseModel):
    unit_id: str
    primitive: Literal["noul", "score", "choice"]
    question_id: str                 # 판단 문항 템플릿 ID + 버전
    distribution: dict[str, float]   # Noul: {"true": p, "false": 1-p}, Score/Choice: API probabilities
    p: float                         # 0~1로 정규화된 긍정 확률/기대값
    confidence: float                # 7.3 정의 (primitive별로 다름)
    uncertainty: float
    entropy: float
    jev_model: str                   # 응답의 버전 ID (예: "jev-1.13.0")
    jev_request_id: str | None       # x-typesafe-request-id (추적용)
    decision_source: Literal["jev", "llm_auditor", "strong_judge", "human"]
    jev_p: float                     # escalation 되어도 원래 JEV 값 보존
    audit_rationale: str | None
    needs_human_review: bool
```

### 6.3 결과 schema

설계방향 문서 15장 schema를 기반으로 binary/probabilistic 값과 진단 정보를 확장한다.

```json
{
  "sample_id": "q-0001",
  "evaluation_model": {
    "primary_judge": "JEV",
    "preprocessor": "gpt-5.6-luna",
    "secondary_judge": "gpt-6-luna",
    "prompt_versions": {"claim_extraction": "v1", "statement_extraction": "v1"},
    "question_versions": {"claim_support": "v1", "chunk_relevance": "v1"}
  },
  "retrieval": {
    "context_precision": 0.87,
    "context_precision_rank": 0.91,
    "context_recall": 0.81,
    "context_recall_binary": 0.83
  },
  "generation": {
    "faithfulness": 0.94,
    "faithfulness_binary": 1.0,
    "answer_relevancy": 0.92
  },
  "confidence": {"faithfulness": 0.96, "context_precision": 0.91, "context_recall": 0.69, "answer_relevancy": 0.94},
  "uncertainty": {"faithfulness": 0.04, "context_precision": 0.09, "context_recall": 0.31, "answer_relevancy": 0.06},
  "escalation": {"total_decisions": 18, "audited": 2, "strong_judged": 0, "human_review": 0},
  "units": [ /* EvalUnit + Decision 목록 (진단용) */ ],
```

## 7. 모듈별 상세 설계

### 7.1 Layer 1 — Preprocessor (Generative LLM)

**책임**: 평가 단위 생성만 담당하며 판단(점수)을 내리지 않는다.

| 기능 | 입력 | 출력 | 사용 metric |
|---|---|---|---|
| Atomic claim extraction | question, answer | `claim[]` | Faithfulness |
| Reference claim extraction | question, reference | `ref_claim[]` | Context Recall |
| Statement extraction | question, answer | `statement[]` | Answer Relevancy |
| Normalization | unit[] | unit[] | 공통 |

구현 사항:

- **Structured output**: JSON schema(`{"claims": [{"text": str, "source_span": str}]}`) 강제. 프록시가 `response_format=json_schema`를 지원하지 않으면 JSON 모드 + pydantic 검증 + 최대 2회 재요청으로 fallback한다 (Phase 0에서 지원 여부 확인).
- **프롬프트 규칙**
  - claim은 단독으로 참/거짓 판정 가능한 원자 문장으로 작성한다.
  - 대명사를 해소한다 (예: "그는" → "아인슈타인은").
  - 수치, 날짜, 단위, 고유명사를 원문 그대로 보존한다.
  - 원문에 없는 정보를 추가하지 않는다.
  - 원문 언어를 유지한다 (한국어 답변 → 한국어 claim). 설계 문서 예시처럼 영어로 변환하지 않는다. JEV는 한국어를 처리하지만 영어보다 정확도가 낮을 수 있으므로(7.2.1), Phase 1의 한/영 비교 결과에 따라 언어 옵션을 둔다.
- **Normalizer**: 공백·구두점 정규화, 완전 중복 제거, 임베딩 없이 문자 n-gram Jaccard ≥ 0.9인 준중복 제거.
- **결정성**: GPT-5 이후 모델은 `temperature`를 지원하지 않으므로 보내지 않고 `seed`만 지정한다. LLM 출력은 결정적이지 않으므로 결과는 `(model, prompt_version, masked_input_hash)` 키로 캐시하여 재실행 시 동일 unit을 재사용한다. 이것이 "deterministic scoring"의 전제다.
- **Edge case**
  - claim 0개 (예: "모르겠습니다") → Faithfulness = `null`, 사유 `no_claims`.
  - reference 없음 → Context Recall 계산 생략, `status=partial`.
  - 과도한 분해 방지: 샘플당 최대 claim 수(기본 30) 초과 시 경고를 기록한다.

### 7.2 Layer 2 — JEV Client (Primary Judge)

#### 7.2.1 JEV API 요약 (docs.typesafe.ai 확인)

| 항목 | 내용 |
|---|---|
| 엔드포인트 | `POST https://api.typesafe.ai/v1/systemone`, `Authorization: Bearer $TYPESAFE_API_KEY` |
| 요청 | `{"model", "state", "questions": {<id>: Question}}`. `state`는 문자열/객체/배열이며, **한 번 입력하면 모든 question이 병렬로 평가**된다 |
| Question | `{"type": "noul"\|"choice"\|"score", "instructions": str\|object\|array, "criteria": ...}` |
| Noul 응답 | `{"noul": 0~1}` = P(yes). **`confidence` 필드 없음** |
| Choice 응답 | `choice`, `probabilities`, `confidence` (옵션 최대 255개) |
| Score 응답 | `score`(확률 가중 기대값, 0~k−1), `legend`, `probabilities`, `confidence` (레벨 2~10개) |
| 모델 | `jev-1.13.0` (alias `jev-latest`, `jev-preview`는 현재 동일). alias는 새 릴리스 시 이동한다 |
| 한도 | 요청당 64k 토큰. **state + 가장 긴 question ≤ 32k** |
| Rate limit | 250k tokens/s, 1,200 req/min. 예고 없이 바뀔 수 있음 |
| 과금 | 입력 토큰당 $0.042/Mtok. 출력은 무료 |
| 오류 | 401, 422(검증 실패), 429, 529(과부하). SDK가 429/529를 backoff로 재시도한다 |
| 언어 | 영어가 주 학습 언어. CJK는 처리되지만 정확도가 영어와 같지 않다 |

**연결 테스트 결과** (2026-09-23, 합성 한국어 샘플, `jev-1.13.0`): 한 요청에 question 6개, 약 0.6초, 입력 597 토큰.

| question | 기대 | 결과 |
|---|---|---|
| claim "1879년에 태어났다" 지원 여부 | 지원 | 0.98 |
| claim "독일 울름에서 태어났다" 지원 여부 | 지원 | 0.98 |
| claim "영국 특허청에서 근무했다" 지원 여부 | 미지원 | 0.01 |
| 출생지 질문에 contexts[0](출생 정보) 관련 여부 | 관련 | 0.99 |
| 출생지 질문에 contexts[1](근무 정보) 관련 여부 | 무관 | 0.06 |
| contexts[0] 관련도 Score(0–3) | 3 | 3.0 (confidence 1.0) |

#### 7.2.2 호출 설계: 샘플 × metric 단위 fan-out

JEV는 state를 한 번 입력받아 여러 question을 병렬로 평가하므로 **unit마다 요청하지 않고, 샘플 × metric마다 요청 1회**로 묶는다. TypeSafe 문서의 parallel questions 예제에서는 이렇게 묶는 방식이 12배 저렴하고 10배 빨랐다.

| Metric | state | questions |
|---|---|---|
| Context Precision | `{"question", "contexts": [...]}` | chunk마다 `Is \`contexts[i]\` useful for answering \`question\`?` |
| Faithfulness | `{"contexts": [...]}` | claim마다 instructions 객체 `{"claim": ..., "question": "Is \`claim\` fully supported by \`contexts\`?"}` |
| Context Recall | `{"contexts": [...]}` | ref_claim마다 같은 구조 |
| Answer Relevancy | `{"question"}` | statement마다 `{"statement": ..., "question": "Does \`statement\` directly address \`question\`?"}` + 전체 answer Score 1개 |

- question id는 모델에 전달되지 않으므로 `unit_id`를 그대로 쓴다 (예: `claim_3`).
- 한도 초과 시: state가 32k 토큰을 넘으면 contexts를 나눠 여러 요청으로 보낸 뒤, claim마다 `max_i P(supported | contexts 묶음_i)`로 집계한다. 토큰 수는 보수적으로 추정한다(문자 수 기반, 한국어는 여유를 크게 둔다).
- 한 요청에 들어가는 question 수가 많으면(예: claim 30개 이상) 입력 64k 한도 안에서 요청을 나눈다.

#### 7.2.3 Judge 인터페이스

JEV API 형태(state 1개 + question 여러 개)에 맞춰 batch 단위로 정의한다. JEV, LLM Judge, Mock이 모두 같은 인터페이스를 구현한다.

```python
class JudgeQuestion(BaseModel):
    unit_id: str
    question_id: str                 # 템플릿 ID + 버전 (예: "claim_support.v1")
    primitive: Literal["noul", "score", "choice"]
    instructions: str | dict
    criteria: dict | list | None = None

class Judge(Protocol):
    async def evaluate(self, state: dict, questions: list[JudgeQuestion]) -> list[RawAnswer]: ...
```

- `JevJudge`: `typesafe_sdk.AsyncTypeSafeClient.system_one()`을 감싼다. `model`은 설정값으로 고정하고(`jev-1.13.0`), 응답의 `model`과 `request_id`를 `Decision`에 기록한다.
- `MockJudge`: `(question_id, unit_id)` 해시로 결정적인 확률을 반환한다. 단위 테스트와 오프라인 개발에 사용한다.

#### 7.2.4 판단 문항 템플릿 (`judge/questions.py`, 버전 관리)

| question_id | primitive | instructions (state 필드를 backtick으로 참조) | metric |
|---|---|---|---|
| `chunk_relevance.v1` | Noul | Is `contexts[i]` useful for answering `question`? | Context Precision (구버전) |
| `chunk_relevance.v2` | Noul | Does `contexts[i]` contain information that answers `question`? + criteria | Context Precision (reference가 없을 때) |
| `chunk_relevance.v3` (기본) | Noul | Does `contexts[i]` contain information used in `reference`, the answer to `question`? + criteria | Context Precision (reference가 있을 때, 없으면 v2로 자동 전환) |
| `claim_support.v1` | Noul | Is `claim` fully supported by `contexts`? | Faithfulness |
| `ref_claim_coverage.v1` | Noul | Is `claim` fully supported by `contexts`? | Context Recall |
| `statement_relevance.v1` | Noul | Does `statement` directly address `question`? | Answer Relevancy (구버전) |
| `statement_relevance.v2` (기본) | Noul | Is `statement` relevant to answering `question`? Judge relevance only, not whether it is true. + criteria | Answer Relevancy |
| `answer_relevance_scale.v1` → v2 (기본) | Score (4단계) | How directly and completely does `answer` address `question`? — Unrelated / Partially relevant / Mostly relevant / Direct and complete | Answer Relevancy (옵션) |
| `grounding_scale.v1` | Score (4단계) | How completely is `answer` grounded in `contexts`? | 진단용 |
| `unsupported_handling.v1` | Choice | How does `answer` handle information absent from `contexts`? — adds_no_unsupported_information / explicitly_marks_uncertainty / hedges / states_unsupported_as_fact | 오류 유형 분석 |

문항 작성 규칙 (JEV 1.13 jaggedness 문서 반영):

- 한 Noul에는 판단 하나만 넣는다. 조건이 두 개면 Noul 두 개로 나누고 코드에서 결합한다.
- 높은 값이 "예"가 되도록 긍정형으로 쓴다. 부정형이나 이중 부정은 쓰지 않는다.
- 경계가 애매하면 `criteria.true` / `criteria.false`로 기준을 명시한다 (예: "fully supported"의 범위).
- 같은 판단을 Noul과 Choice로 물었을 때나, 질문과 그 부정형 사이의 확률 관계(`P(a) + P(not a) = 1`)는 보장되지 않는다. 판단 방향은 한 가지로만 묻고 `P(false) = 1 − noul`로 계산한다.
- 문항 변경은 새 버전 ID로만 한다. 기존 결과와 비교할 수 있게 하기 위해서다.

#### 7.2.5 기타 구현 사항

- 응답 검증: Noul은 0~1 범위를, Choice/Score는 확률 합이 1에 가까운지(±1e-3) 확인한다. 벗어나면 재정규화하고 경고를 남긴다. NaN이거나 누락되면 해당 unit을 `error`로 기록한다.
- 동시성: `asyncio.Semaphore(JEV_MAX_CONCURRENCY)`. 재시도는 SDK `RetryPolicy`에 맡긴다.
- 캐시 키: `(question_id, instructions_hash, masked_state_hash, jev_model)`. 모델 버전을 키에 넣어 alias가 이동해도 캐시가 섞이지 않게 한다.
- Prompt injection: contexts에 모델을 조종하는 문장이 섞이면 판단이 흔들릴 수 있다 (문서의 알려진 한계). 벤치마크에 injection 샘플을 넣어 영향을 측정한다.

### 7.3 Uncertainty 계산 (`scoring/uncertainty.py`)

| 값 | Noul (binary) | Score / Choice (k-class) |
|---|---|---|
| `p` | `noul` | Score: `score / (k − 1)`, Choice: 목표 옵션의 확률 |
| `confidence` | `max(noul, 1 − noul)` (API가 주지 않으므로 직접 계산) | **API가 반환한 `confidence`를 그대로 사용** |
| `uncertainty` | `1 − confidence` | `1 − confidence` |
| `entropy` | `−Σ p log2 p` (0~1) | `−Σ p log k` 정규화 (0~1) |

- API의 Choice/Score confidence는 `max_i P_i`가 아니다. 분포가 얼마나 퍼졌는지를 보는 값으로, 대략 `(k·max_i P_i − 1)/(k − 1)`이다. 예: 3개 옵션에서 max가 0.88이면 약 0.81. 비교 분석용으로 `max_prob`도 함께 저장한다.
- 따라서 **Noul confidence와 Choice/Score confidence는 척도가 다르다.** routing threshold는 primitive별로 따로 둔다 (7.4).
- Score의 기대값은 threshold 비교에는 쓸 수 있지만, 레벨 사이 값을 정밀한 크기로 해석하면 안 된다 (문서의 알려진 한계).

Metric 단위 confidence/uncertainty 집계:

- 기본: 해당 metric에 포함된 decision의 `confidence` 평균.
- 함께 저장: `confidence_min` (가장 불확실한 unit), 기준 미만 unit 비율.

### 7.4 Layer 3 — Router & LLM Auditor

**Routing 규칙** (threshold는 설정값이며 primitive별로 따로 둔다):

```text
confidence >= CONF_ACCEPT (0.85)            → decision_source = jev
CONF_AUDIT (0.60) <= confidence < 0.85      → LLM Auditor 재판단
confidence < CONF_AUDIT                     → Strong Judge 재판단 + needs_human_review = true
```

- Noul 기준으로 보면 `noul ≥ 0.85` 또는 `≤ 0.15`면 JEV 판정을 그대로 쓰고, `0.40 < noul < 0.60`이면 Strong Judge로 보낸다.
- Choice/Score용 threshold(`RAGAS_JEV_CONF_ACCEPT_CHOICE` 등)는 따로 두고, 초기값은 같게 시작해 Phase 5에서 각각 calibration한다. Noul에서 맞춘 threshold를 Choice에 그대로 옮기지 않는다.

**Auditor 동작**:

- 입력: JEV와 동일한 판단 문항 + 입력 + JEV 분포(옵션, bias 비교 실험용으로 on/off).
- 출력(JSON): `{"verdict": "true|false", "confidence": 0~1, "rationale": str}`.
- 병합 정책:
  - `p` ← Auditor verdict 기반 확률 (verdict=true → auditor confidence, false → 1 − auditor confidence).
  - `jev_p`에는 원래 JEV 값을 보존한다.
  - `decision_source`를 기록한다.
- JEV와 Auditor가 불일치하고 Auditor confidence가 낮으면 `needs_human_review=true`로 표시한다.
- **Human review queue**: `needs_human_review` unit을 CSV로 export하고 (마스킹 텍스트만), 라벨을 import하면 `decision_source=human`으로 덮어쓴다.
- **Escalation off 모드** (`--no-audit`): JEV-only 벤치마크 baseline으로 사용한다.

### 7.5 Deterministic Scorer

모든 scorer는 `list[Decision] → MetricResult`의 **순수 함수**이며 외부 호출을 하지 않는다.

| Metric | Probabilistic | Binary | 비고 |
|---|---|---|---|
| Faithfulness | `mean(p_claim)` | `count(p ≥ τ) / N` | τ = `DECISION_THRESHOLD` (0.5) |
| Context Precision (soft) | `mean(p_chunk)` | `count(p ≥ τ) / K` | |
| Context Precision (rank) | `Σ w_i·p_i / Σ w_i` | — | `w_i = (K − i + 1) / K` (K=5면 1.0, 0.8, …, 0.2로 설계 문서 예시와 일치) |
| Context Precision (RAGAS AP@K) | — | 기존 RAGAS 공식 | 벤치마크 비교용 |
| Context Recall | `mean(p_ref_claim)` | `supported / total` | reference 필수 |
| Answer Relevancy (statement) | `mean(p_statement)` | `count(p ≥ τ) / N` | 기본 방식 |
| Answer Relevancy (scale) | `E[s] / 3` | — | 옵션, 진단용으로 병행 저장 |

- 부동소수 결정성: 입력 decision을 `unit_id` 기준으로 정렬한 뒤 합산한다.
- 데이터셋 집계: metric별 mean, median, std, 95% bootstrap CI, `null` 제외 개수.

### 7.6 Pipeline 오케스트레이션

```text
load samples
  → PII Guard (마스킹)
  → Preprocess (claims / ref_claims / statements, 병렬)
  → Build judge requests (metric별 unit × question)
  → JEV judge (병렬, 캐시)
  → Router → Auditor / Strong Judge (해당 unit만)
  → Scorer (metric별)
  → Assemble result JSON
  → Report
```

- metric 선택 실행: `--metrics faithfulness,context_precision`.
- 샘플 단위 실패 격리: 한 샘플이 실패해도 전체 실행은 계속되며, 실패 샘플은 `status=error`와 원인을 기록한다.
- 체크포인트: 결과를 샘플 단위 JSONL로 append하고, 재실행 시 완료된 `sample_id`는 건너뛴다.

- 같은 v2 문항에서 LLM Judge와 비교: `gpt-6-luna`와 한국어 F1 동률(0.571). 가장 나은 `gpt-6-sol`은 F1 0.606(JEV −0.035), AUROC는 비슷(0.876 vs 0.883).
- 모델 역할 확정: 기준선 `gpt-6-sol`, Auditor `gpt-6-luna`. Auditor 모의 실험에서 JEV conf < 0.85(약 37%)만 재검증하면 한국어 F1 0.571 → 0.600.
- 남은 결정: F1 목표치 확정 (리포트 7장), 불일치 사례 검수.

### Phase 2 — Faithfulness (1.5주)

| 작업 | 산출물 |
|---|---|
| LLM client, claim extraction 프롬프트 v1 | `claim_extractor.py` |
| Normalizer (중복 제거) | `normalizer.py` |
| `claim_support.v1` 문항, 긴 context 처리 전략 | |
| 수치 claim 보완 검사: claim의 숫자·날짜·단위를 코드로 추출해 contexts에 있는지 대조한다. JEV는 수치 비교가 약하다 | `numeric_check.py` |
| state 구성 A/B: contexts 전체 1회 판단 vs chunk별 판단 후 max (distractor 영향 측정) | 비교 결과 |
| probabilistic / binary scorer | `faithfulness.py` |
| 검증: claim extraction 품질(누락·환각·과분해 수동 검수 30샘플), granularity 분포, entailment 정확도, hallucination 주입 샘플 탐지율 | Phase 2 검증 리포트 |

**Exit criteria**: 수동 검수에서 claim 누락률과 환각 claim 비율이 합의된 기준 이하이고, 주입한 hallucination 탐지 recall이 기준 이상이다.

**상태: 완료 (2026-09-24)**. Phase 1과 같은 기준(기준선 `gpt-6-sol` F1 − 0.05 이내 + AUROC ≥ 0.85)으로 통과 판정했다.

**진행 결과 (2026-09-24)**: [Phase 2 검증 리포트](reports/phase2_faithfulness.md) 참조. RAGTruth QA(영어 전문가 라벨, 320응답)와 MIRACL-ko 합성 hallucination 세트(192응답)로 검증했다.

- JEV `claim_support.v1` + joint: RAGTruth 응답 F1 0.781, claim AUROC 0.913, ECE 0.080. 기준선 `gpt-6-sol`(F1 0.761, AUROC 0.904)과 같거나 낫다.
- v2 문항과 per_chunk 방식은 이득이 없어 기본값(v1, joint)을 유지했다. 수치 검사는 진단 정보로만 쓴다.
- 남은 결정: 통과 판정(Phase 1 기준 적용 시 통과), `claim_extraction.v2`(출처 주장·추론·세부 정보 누락 보완), `claim_support.v3`(세상 지식 배제) A/B.

| 작업 | 산출물 |

| `statement_relevance.v1` (Noul) + `answer_relevance_scale.v1` (Score) | |

**진행 결과 (2026-09-24)**: [Phase 4 검증 리포트](reports/phase4_answer_relevancy.md) 참조. WikiEval(RAGAS 논문 데이터, 50문항)과 MIRACL-ko/en 합성 세트(무관 문장 삽입, 틀린 답변, 답하지 않는 답변)로 검증했다.

- 남은 결정: 통과 판정 (기준선 대비 모든 판별 지표에서 같거나 나음).

### Phase 5 — Secondary LLM Judge (1.5주)

| 작업 | 산출물 |
|---|---|
| Router, LLM Auditor, Strong Judge | `audit/` |
| Human review export/import | `review_queue.py` |
| threshold calibration: validation set에서 confidence 구간별 JEV 정확도(reliability diagram)를 측정하고 `CONF_ACCEPT`, `CONF_AUDIT` 재설정 | calibration 리포트 |
| 언어별 p 보정(예: isotonic)과 판정 threshold. Phase 1에서 한국어 ECE 0.22, 최적 F1 threshold 0.85가 확인됨 | 보정 모델, 언어별 설정 |
| 비용·정확도 trade-off 곡선 (threshold별 escalation 비율 vs 정확도) | trade-off 차트 |

**Exit criteria**: escalation 비율과 정확도 향상폭이 정량화되고, 운영 threshold가 근거와 함께 확정된다.

**상태: 완료 (2026-09-24)**. Exit criteria(escalation 비율과 정확도 향상 정량화, threshold 확정)를 충족해 통과 판정했다.

**진행 결과 (2026-09-24)**: [Phase 5 검증 리포트](reports/phase5_routing_calibration.md) 참조. Phase 1~3의 저장된 판정으로 보정 교차 검증과 routing grid 시뮬레이션을 했다.

- 확률 보정(질문·언어별 isotonic)을 기본으로 켠다. ECE 0.07~0.18 → 0.01~0.02. Context Precision은 보정만으로 `gpt-6-sol` 단독보다 κ가 높다.
- 계획서의 단일 threshold(0.85 / 0.60) 대신 metric별 정책을 확정했다: Context Precision은 conf < 0.60만 Strong Judge, Faithfulness는 conf < 0.65만 Auditor, Context Recall은 routing 없음. 세 metric 모두 LLM 단독과 같거나 낫고 샘플당 LLM 호출은 0~0.40회.
- Strong Judge를 `gpt-6-astra`에서 `gpt-6-sol`로 변경. 사람 검토는 LLM이 JEV와 반대로 판정한 unit만 대상.
- 한계: 보정이 라벨 기본 비율을 학습하므로 서비스 데이터에서는 도메인 라벨로 재보정이 필요하다.

### Phase 6 — Benchmark 및 문서화 (1주)

- 비교 대상 3종: (1) 기존 RAGAS / LLM Judge, (2) JEV-only (`--no-audit`), (3) Hybrid RAGAS-JEV.
- 비교 지표 (설계방향 문서 17장):

| 지표 | 산출 방법 |
|---|---|
| Human agreement | Cohen's κ (unit 단위), 샘플 점수 Pearson/Spearman |
| Accuracy / Precision / Recall / F1 | unit 판정 vs human label |
| Rank correlation | 시스템 간 샘플 순위 Kendall τ |
| Calibration Error | ECE (10-bin), reliability diagram |
| Evaluation variance | 동일 입력 N회 반복 시 점수 표준편차 (캐시 off) |
| Latency | 샘플당 p50/p95 |
| Cost | 샘플당 LLM 토큰 수, JEV 요청 수와 입력 토큰 × $0.042/Mtok |
| Repeatability | 반복 실행 간 binary 판정 일치율 |
| Uncertainty quality | uncertainty와 오판 여부의 AUROC (불확실할수록 틀리는지 검증) |

- 산출물: `benchmark/reports/benchmark_YYYYMMDD.md`, README 사용법.

**상태: 완료 (2026-09-24)**. 비교 대상 3종(+ 공식 RAGAS)과 설계방향 17장의 비교 지표를 산출해 통과 판정했다.

**진행 결과 (2026-09-24)**: [Phase 6 벤치마크 리포트](reports/phase6_benchmark.md) 참조. 공식 `ragas` 0.4.3(판정 `gpt-6-sol`), 이 파이프라인의 LLM Judge(`gpt-6-sol`), JEV만, Hybrid(보정 + routing)를 Phase 1~4 데이터로 비교했다.

- Hybrid가 Context Precision(사람 라벨 Spearman 0.681 / 0.567), Faithfulness(RAGTruth AUROC 0.830, F1 0.790), Answer Relevancy(WikiEval 0.92)에서 1위. Context Recall은 RAGAS가 1위(Pearson 0.909 / 0.944)이고 Hybrid와 차이는 0.006 이하.
- 재현성: 같은 입력 2회에서 응답 판정이 뒤집힌 비율 JEV 0%, LLM Judge 1.2%, RAGAS 6.2%.
- 판정용 LLM 호출: Hybrid 샘플당 0~0.40회, RAGAS 1~2회.
- 제약: 1차 비교에서 RAGAS Context Precision(reference 필요)과 Answer Relevancy(임베딩 필요)는 실행하지 못했다. `ragas` 실행을 위해 가상환경을 Python 3.12로 바꿨다.

**후속 작업 (2026-09-24)**

- 도메인 재보정 도구: `ragas-jev calibration sample / fit`, [도메인 재보정 가이드](도메인_재보정_가이드.md).
- reference 기반 Context Precision 비교: RAGAS `ContextPrecision`이 1위(AP Pearson 0.638 / 0.696). 기본 보정 Hybrid는 분포 차이(관련 비율 18% → 44%)로 최하위(0.390 / 0.516)였고, 그 세트 라벨로 재보정하면 0.558 / 0.614로 회복했다. 재보정이 필수라는 근거.
- RAGAS Answer Relevancy(로컬 다국어 임베딩): WikiEval 0.72, 무관 문장 삽입 감지 0.61 / 0.49로 JEV(0.92, 0.98 / 0.95)보다 낮고, 틀린 답을 낮게 매긴다.
- `chunk_relevance.v3`(reference 사용) 추가: JEV만 v3가 AP Pearson 0.674 / 0.672로 RAGAS(0.638 / 0.696)와 같은 수준이 됐고(판정용 LLM 호출 0회), Hybrid v3가 순위 일치·오차·chunk κ 1위. Context Precision 기본 문항으로 채택.
