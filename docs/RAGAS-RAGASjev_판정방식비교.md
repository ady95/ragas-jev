# RAGAS와 RAGAS-JEV의 판정 방식 비교: 임계값과 치우침

- 기준: 2026-09-26, ragas-jev 0.2.0, 비교 대상 ragas 0.4.3
- 관련 문서: [평가 항목 비교](ragas-jev_평가항목.md), [Phase 5 리포트](reports/phase5_routing_calibration.md), [Phase 6 리포트 9절 (0.2.0 기본값 재측정)](reports/phase6_benchmark.md), [도메인 재보정 가이드](도메인_재보정_가이드.md)

0.2.0에서 확률 보정을 기본으로 끄자, Hybrid 성능 일부가 떨어졌습니다([Phase 6 리포트 9절](reports/phase6_benchmark.md)). 이 문서는 두 가지를 정리합니다. 첫째, RAGAS-JEV가 쓰는 재판정 기준(임계값)은 무엇인가. 둘째, 왜 RAGAS에서는 같은 문제가 보이지 않는가.

## 1. 재판정 기준 = 판정 신뢰도에 대한 임계값

ragas-jev는 unit(claim, chunk, statement)마다 아래 순서로 임계값 세 개를 씁니다.

```
JEV 확률 p  →  신뢰도 = max(p, 1−p)
                 ├─ 신뢰도 ≥ accept          → JEV 판정 유지
                 ├─ audit ≤ 신뢰도 < accept  → Auditor(gpt-6-luna)가 다시 판정
                 └─ 신뢰도 < audit           → Strong Judge(gpt-6-sol)가 다시 판정
최종 p ≥ 0.5 → "예"(지지됨 / 관련 있음)
```

| 임계값 | 기본값 | 역할 |
|---|---|---|
| 판정 임계값 (`RAGAS_JEV_DECISION_THRESHOLD`) | 0.5 | 확률을 예/아니오로 나눕니다. 이진 점수(`*_binary`)와 AP 계산에 씁니다 |
| `accept` | Context Precision 0.60, Faithfulness 0.65, Context Recall·Answer Relevancy 0 | 신뢰도가 이 값 이상이면 JEV를 믿습니다. 0이면 재판정을 하지 않습니다 |
| `audit` | Context Precision 0.60, Faithfulness 0 | 신뢰도가 이 값 미만이면 강한 모델로 보냅니다 |

`accept`와 `audit`는 Phase 5에서 **보정된 확률**로 여러 조합을 시험해 고른 값입니다(`DEFAULT_METRIC_POLICIES`). 그래서 보정을 끄면 이 값들이 맞지 않게 됩니다.

- **Context Precision (reference 없음)**: 재판정 비율이 5.8%에서 7.5%로 늘었습니다. 그런데 순위 상관은 재판정을 전혀 하지 않은 "JEV만"(0.621)보다 낮은 0.601이었습니다.
- **Faithfulness**: 원래 확률이 "지지" 쪽으로 치우쳐 신뢰도가 높게 나옵니다. 그래서 재판정 비율이 8.8%에서 6.5%로 줄었습니다.

## 2. 왜 RAGAS에는 이런 문제가 없나

RAGAS에 문제가 없는 것이 아니라, **같은 문제가 조절할 수 없는 형태로 숨어 있습니다.**

### 2.1 RAGAS는 확률 대신 0/1만 받는다

| | RAGAS | RAGAS-JEV |
|---|---|---|
| 판정 결과 | LLM이 0 또는 1을 답합니다 | JEV가 0~1 확률을 줍니다 |
| 예/아니오를 가르는 기준 | **LLM 안에 숨어 있습니다.** 모델과 프롬프트가 정합니다 | 판정 임계값(0.5)으로 **밖에 드러나 있습니다** |
| 판정 신뢰도 | 없음 | 있음 |
| 재판정과 보정 | 없음 | 있음 (선택) |

RAGAS에서는 LLM이 스스로 "이 정도면 지지된다"는 선을 긋습니다. 사용자가 조정할 임계값이 없으니, "임계값이 데이터에 안 맞는다"는 문제도 겉으로 보이지 않습니다.

### 2.2 하지만 치우침은 RAGAS에도 똑같이 있다

LLM 안에 숨은 기준은 모델, 프롬프트, 데이터에 따라 움직입니다. 실제로 이렇게 관찰됐습니다.

| 관찰 | 근거 |
|---|---|
| 판정이 한쪽으로 치우침 | bench40(별도 실험, 노동법 도메인 합성 40건)에서 RAGAS Faithfulness는 정답보다 평균 **0.12 낮게** 나왔습니다. 비사실 문장을 감점하고, 계산으로 나온 claim을 거부했습니다 |
| 판정 모델을 바꾸면 기준이 바뀜 | bench40에서 판정 모델을 `gpt-6-luna`에서 `gpt-6-sol`로 바꾸자 Context Precision MAE가 0.050에서 0.002로 달라졌습니다. 반대로 sol은 계산 결과 claim을 더 엄격하게 거부했습니다 (R-CALC Faithfulness MAE 0.083 → 0.250) |
| 같은 입력에도 결과가 달라짐 | RAGTruth 응답 80개를 두 번 평가하면 hallucination 판정이 6.2% 뒤집혔습니다 (JEV 0%) |
| 정의 차이를 고칠 수 없음 | reference가 없으면 `ContextRelevance`밖에 쓸 수 없어, 사람 라벨과의 상관이 0.111 / 0.253(한국어 / 영어)에 그쳤습니다 |

RAGAS-JEV에서는 치우침이 "보정이 안 맞는다"로 드러납니다. RAGAS에서는 같은 치우침이 "점수가 이유 없이 낮거나 높다"로 나타납니다. 차이는 **고칠 수단이 있느냐**입니다.
- **RAGAS**: 프롬프트나 판정 모델을 바꾸는 방법밖에 없습니다.
- **RAGAS-JEV**: 임계값을 조정하거나, 도메인 라벨로 다시 보정할 수 있습니다.

### 2.3 이번 문제는 선택 기능에서 생겼다

보정과 재판정을 모두 빼고 **JEV만** 쓰면, 조정할 값은 판정 임계값 0.5 하나뿐입니다. 이 상태로도 RAGAS와 비교하면 다음과 같습니다(Phase 6).

| 지표 | RAGAS | JEV만 |
|---|---|---|
| Faithfulness AUROC (RAGTruth) | 0.790 | **0.809** |
| Context Precision, 질문만 (MIRACL Spearman, 한국어 / 영어) | 0.111 / 0.253 | **0.621 / 0.544** |
| Context Precision, reference 사용 (v3, AP Kendall) | 0.459 / 0.518 | **0.518 / 0.523** |
| Answer Relevancy (WikiEval 쌍 정확도) | 0.720 | **0.920** |
| Context Recall (Pearson) | **0.909 / 0.944** | 0.878 / 0.920 |

이 문서에서 다룬 문제는 Hybrid의 부가 기능인 **확률 보정과 LLM 재판정**을 쓸 때 생깁니다. 두 기능은 JEV가 확률과 신뢰도를 주기 때문에 가능한 기능이고, 대신 데이터에 맞는 임계값을 골라야 하는 부담이 따릅니다.

비유하면 RAGAS는 합격·불합격 도장만 찍고, JEV는 몇 점인지 알려 줍니다. 점수를 받으면 커트라인을 정해야 하는 수고가 생깁니다. 대신 커트라인 근처의 애매한 사례를 골라 다시 볼 수 있습니다.

## 3. 운영 시 권장

| 상황 | 권장 |
|---|---|
| 평가 데이터가 기본 보정의 학습 데이터(공개 Wikipedia·웹 QA)와 비슷함 | `--calibrate`. 보정과 재판정 기준이 함께 맞습니다 |
| 서비스 도메인이고 라벨이 없음 | 0.2.0 기본값(보정 없음). 절대 점수보다 순위 비교에 쓰는 것이 안전합니다. 재판정 기준은 보정 없는 확률에 맞게 다시 조정할 수 있습니다 (라벨 불필요, 저장된 판정으로 계산) |
| 서비스 도메인 라벨이 있음 | [도메인 재보정](도메인_재보정_가이드.md) 후 `--calibration 파일` |
| 합격 기준처럼 절대값이 중요함 | 도메인 재보정을 먼저 하세요. 보정이 맞지 않으면 절대값의 오차가 가장 크게 나타납니다 |
